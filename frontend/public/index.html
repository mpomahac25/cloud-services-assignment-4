Implementation

The application was first created and tested locally using Docker Compose. It consists of three containers: a frontend Node.js application, a backend Node.js/Express REST API, and a MySQL database.

After local testing, the frontend and backend images were built and pushed to Docker Hub. The application was then deployed to CSC Rahti using Kubernetes/OpenShift resources.

Only the frontend is publicly accessible. The backend and database are available only through internal Kubernetes Services. This can be seen by looking at Networking -> Services on the CSC Rahti console and seeing 3 services there (figure 1), then looking at Networking -> Routes and seeing that there is only one route which is pointing to the frontend service (figure 2).

Database Persistence

The MySQL database uses a Kubernetes PersistentVolumeClaim so that the database files are stored separately from the MySQL pod itself.

To test the persistence, I first increased the database-backed counter to a known value (figure 1).

Next, I took a screenshot of the currently running pods for reference (figure 2).

I then manually deleted the MySQL pod and immediately saw the old pod terminating and a new one being created (figure 3).

The new MySQL pod was created using the same persistent volume as the old one. Because of this, once the pod was running, the app still displayed the same counter value of 6, which confirmed that the data was truly being stored inside the persistent volume and not inside the pod itself.

Result

The database data remained available after replacing the MySQL pod. This shows that the PersistentVolumeClaim successfully separates the lifetime of the database data from the lifetime of individual pods.

Pod Recovery

The backend Deployment was configured to run one replica. To test Kubernetes recovery, I manually deleted the running backend pod. Similar to the database persistence experiment, as soon as I deleted the original backend pod a new one started spinning up (figure 1).

The application continued functioning normally after the replacement pod had started.

What Recreated the pod?

The backend is managed by a Kubernetes Deployment. The Deployment manages a ReplicaSet (figure 2), which is responsible for maintaining the requested number of pod replicas.

When the backend pod was deleted, the ReplicaSet detected that the desired replica count of one was no longer satisfied and created a new pod automatically.

Backend Scaling

The backend Deployment was initially configured with one replica (figure 1). To test Kubernetes scaling, the replica count was increased from one to three (figure 2).

Kubernetes created two additional backend pods so that three replicas were running at the same time (figure 3).

Service Communication

The frontend did not need to know the address of any individual backend pod. It continued sending requests to backend-service:3000.

The backend Service selects pods using their labels and routes requests to the available backend replicas. After the scaling test, the backend was returned to one replica.

Week 5 Questions & Answers

1. What is a Web Application Firewall (WAF) and what kinds of attacks does it defend against? Where would you place one in the three-container architecture you built in Week 4?

A Web Application Firewall is a firewall designed specifically for HTTP/HTTPS traffic going to a web app. Unlike a normal network firewall, which mostly works with things such as IP addresses, ports and protocols, a WAF can inspect the contents of HTTP requests and block those which appear to be malicious.

It can be useful for detecting and blocking some common web-based attacks, such as SQL injection or cross-site scripting (XSS), along with blocking suspicious request patterns, malformed requests, and attempts to access app paths which shouldn't normally be accessible. However, a WAF should only be seen as an additional layer of protection and shouldn't be seen as a replacement for input validation performed by the web app itself, nor an excuse to not have the web app's code be safe-by-design. The latter point is especially important in current times due to the implementation of the EU's Cyber Resilience Act (CRA).

In the 3-container app built last week, I'd put the WAF just before the Rahti route, as this maximizes the efficiency of the WAF due to it being placed between the internet and the component which exposes the app to the internet. In essence: Internet -> WAF -> Rahti route -> Frontend -> ...

2. What is YAML and why has it become the default configuration format for Kubernetes/Rahti manifests? Compare it briefly to JSON.

YAML is a human-readable data format, commonly used for configuration files and/or representing structured data. Kubernetes/Rahti manifests use it as the de facto default due to the format being relatively easy to read and edit by humans, even in cases where there is a long chain of nested data.

JSON, like YAML, is a way to represent structured data, but requires more code-like syntax such as braces, brackets, quotation marks, etc. Kubernetes itself can work with both JSON and YAML, with YAML being the more common preference due to being more easily read by humans.

A short comparison between YAML and JSON. Let's take the example of scaling the backend, where we needed to change the number of replicas for the backend. In YAML format, we had:

spec:
    replicas: 3

The equivalent JSON format would be:

{
    "spec": {
        "replicas": 3
    }
}

3. List some public APIs and describe a realistic integration you could add to the backend you built in Week 4.

There are countless public APIs available which could be integrated. One such example is the Frankfurter.dev free currency converter API, which is integrated into this application. Due to the original application being a simple persistent button counter, there's not that many APIs which come to mind that would fit the "theme". Maybe an idea could be to have the button send an API request to some random image service API (by random meaning an image service API which will give a random image when a GET request is received), and have the image by dynamically displayed and changed as the button is clicked more and more times.

However, I decided to integrate the currency converter API to maintain the trend of random functionalities. The calls to the actual API URL are done from a new express server which is running inside the currency-service container. The currency-service express server receives requests from the backend server, which in turn receives the requests from the frontend server via the middleware proxy. This gives us the chain: Frontend -> Backend -> Currency service -> Frankfurter API

In addition, the original chain of "Frontend -> Backend -> Database" still exists, as seen by the persistent button click counter.

4. What are open data portals and why does choosing the right open-data format matter for reuse?

An open data portal is a service where organisations such as public authorities publish datasets, which other people and/or applications can then use for their own purposes. One such example would be the European data portal. Since the datasets come from public authorities, they usually contain data such as statistics, geographical information, public sector records, and similar.

A portal usually provides metadata describing the datasets, and may in addition provide downloadable files, APIs, or links to the organization which published the data. The format of the data being provided matters because the format will determine what uses the data can be put to. For example, a PDF file with tables is great for data which needs to be read by a human, but is quite bad for use with any app. Alternatively, a CSV file is easy for an app to parse and use the data provided through it, but is rather difficult for humans to read and understand.

When it comes to reusability, it's preferable for data to be in a machine-readable format, such as CSV, JSON, XML, or similar, as it gives the dataset a broader way of how it can be used, while formats focused on human readability are effectively only going to be useful for reading by a human.

Week 6 Questions

1. Explain the difference between Continuous Integration, Continuous Delivery and Continuous Deployment

Continuous Integration (CI) means that code changes are regularly merged into the main repository and automatically checked, for example by building the application and running automated tests. The main goal is to detect integration problems early instead of finding them only after many changes have been combined.

Continuous Delivery extends this idea by also preparing the application for deployment automatically. A successful pipeline might build a container image, run tests and push the image to a registry. The application is then ready to be deployed, but the actual production deployment still requires a manual decision or approval.

Continuous Deployment further builds on this idea by removing the need for any manual production deployment, and instead automatically deploys to production the latest build which passed automated tests.

In this project, the workflow files are closest to Continuous Deployment. The workflow files get triggered when the corresponding VERSION files are updated in the repo, then the Docker containers are built and pushed to Docker Hub, and finally the Rahti deployment(s) are updated to use the latest version of the container.

2. Describe the structure of a GitHub Actions workflow (triggers, jobs, steps). What would a minimal pipeline for the app you built in Week 4/5 need to do?

A GitHub Actions workflow is defined in a YAML file under .github/workflows/. A workflow first defines its trigger, which determines when it runs. For example, a workflow can run whenever something is pushed to the main branch. In this project the workflows trigger when the VERSION file on a specific repo path is updated, and additionally they have a workflow_dispatch option to be able to manually trigger a build if needed (mainly used for testing here).

A workflow contains one or more jobs. Each job runs on a selected runner such as Ubuntu. Runners can be either ones provided by GitHub which consumes allocated GitHub Actions minutes, or self-hosted runners which are user-owned machines configured for running GitHub Actions workflows at no GitHub Actions minutes cost. A job then contains multiple steps, which are executed in order. Steps can either run shell commands or use existing GitHub Actions, such as an action for logging in to Docker Hub.

For this application, the minimum deployment pipeline needs to:

  1. Check out the source code
  2. Determine the version for the new container build(s) -> VERSION files in this case
  3. Log in to Docker Hub
  4. Build the container image
  5. Push the built image to Docker Hub
  6. Install or make the OpenShift CLI available
  7. Log in to Rahti using a stored token
  8. Update the corresponding deployment using oc set image
  9. Wait for the new deployment rollout to finish successfully

3. Explain the difference between a liveness probe and a readiness probe in Kubernetes/Rahti. What happens when each one fails?

A liveness probe checks whether the application inside a container is still functioning. If the liveness probe repeatedly fails, Kubernetes considers the container unhealthy and restarts it.

A readiness probe checks whether the application is currently able to receive normal traffic. If the readiness probe fails, the container can continue running, but the Pod is marked as not ready and it is not used as a ready endpoint for its Service.

For example, the backend in this project uses /api/health for its liveness probe and /api/ready for its readiness probe. The readiness endpoint also checks whether the backend can communicate with the MySQL database.

I also tested readiness failure by deliberately configuring an invalid readiness path for the currency service. The new Pod remained running but stayed at 0/1 ready. Because the Deployment used a rolling update strategy, the previous healthy Pod remained available while the new Pod was not added as a ready Service endpoint.

4. Why should secrets (registry tokens, cluster login tokens) never be hard-coded into a CI/CD pipeline file? How does GitHub Actions handle this instead?

Secrets such as Docker registry tokens and cluster login tokens should never be written directly into a workflow YAML file because the workflow is normally stored in the Git repository. Anyone with access to the repository could then see the credentials, and they could also remain visible in the Git history even if they were removed later.

If a repository was made public accidentally, hard-coded credentials could allow someone to push malicious container images or access the deployment environment.

GitHub Actions provides repository secrets for this purpose. The secret value is stored separately from the repository and can be referenced from the workflow without putting the actual credential into the YAML file. For example, the Docker Hub token is being accessed by using ${{ secrets.DOCKERHUB_TOKEN }}.

Non-sensitive configuration, such as the Docker Hub username, Rahti server address and Rahti namespace, can instead be stored as normal GitHub repository variables. In this project, the actual authentication tokens are therefore kept outside the source code while the workflow only contains references to them.

CI/CD Pipeline

Separate GitHub Actions workflows were created for the frontend, backend and currency service (figure 1). Each component contains its own VERSION file, and the corresponding workflow is triggered only when that VERSION file is changed on the main branch.

When triggered, the workflow reads the version, verifies that the same Docker image version does not already exist, builds the container image, pushes it to Docker Hub, logs in to Rahti and updates the corresponding Deployment using the OpenShift CLI. The workflow then waits for the rollout to complete successfully. Below is an image (figure 2) showing a successful workflow run with all of the steps visible.

This means that changing application code alone does not automatically release it. Updating the VERSION file acts as an explicit release action (figure 3), and only the component whose version was changed is rebuilt and deployed.

Automatic Deployment

After the container image was pushed to Docker Hub, GitHub Actions used oc set image to update the corresponding Rahti Deployment (figure 4). This caused Rahti to create a new Pod using the newly released container version.

Running Versions

Each application component reads its VERSION file when it starts and provides the value through a version endpoint (figure 5). The frontend displays the versions currently running in Rahti (figure 6), making it possible to verify that the expected container releases were deployed.

Liveness and Readiness Probes

Liveness and readiness probes were configured for the frontend, backend and currency service (figure 1). The liveness probes check whether the application processes are running, while the readiness probes determine whether the Pods are currently able to receive normal traffic.

Readiness Failure Test

The currency service readiness probe was deliberately changed to point to an invalid endpoint (figure 2). The replacement Pod started and remained running, but its readiness state stayed at 0/1 because the readiness probe failed (figure 3).

Since the Deployment uses a rolling update strategy, the previous healthy Pod remained running while the replacement Pod was not ready (figure 3). This allowed the Service to continue using the old healthy Pod instead of routing traffic to the new unhealthy one.

Structured Logging

Structured request logging was added to the frontend, backend and currency service (figure 4). Each request produces a JSON log entry containing information such as the timestamp, service name, HTTP method, request path, response status and request duration (figure 5). The log outputs are taken from local testing via docker-compose for easier demonstration of the multiple implementations.

Example Alert

One useful production alert could monitor the percentage of HTTP 5xx responses. For example, an alert could be triggered if more than 5% of requests fail continuously for five minutes. Using a threshold and a time period instead of alerting on every individual error would reduce unnecessary alerts and help avoid alert fatigue.

Problems Encountered

One problem occurred when the GitHub Actions workflow attempted to log in to Rahti. The Rahti server address had been stored as a repository variable, but the workflow initially referenced it as a secret. This resulted in the oc command receiving no server URL. The workflow was corrected to use vars.RAHTI_SERVER.

Another problem occurred after VERSION files were added to the application. The services attempted to read the VERSION file when they started, but the Dockerfiles did not copy the file into the container images. This caused the new Pods to enter CrashLoopBackOff. COPY VERSION ./ was added to each Dockerfile and new container versions were released.
