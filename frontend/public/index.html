Implementation

The application was first created and tested locally using Docker Compose. It consists of three containers: a frontend Node.js application, a backend Node.js/Express REST API, and a MySQL database.

After local testing, the frontend and backend images were built and pushed to Docker Hub. The application was then deployed to CSC Rahti using Kubernetes/OpenShift resources.

1. Application Architecture

Only the frontend is publicly accessible. The backend and database are available only through internal Kubernetes Services. This can be seen by looking at Networking -> Services on the CSC Rahti console and seeing 3 services there (figure 1), then looking at Networking -> Routes and seeing that there is only one route which is pointing to the frontend service (figure 2).

2. Docker Images

Separate Docker images were created for the frontend and backend (figure 3 and 5). Version 1.0.0 of both images was initially pushed to Docker Hub (figure 4 and 6). The official MySQL 8.4 image was used for the database.

The frontend image: mpomahac25/cloud-assignment-w4-frontend:1.0.0

The backend image: mpomahac25/cloud-assignment-w4-backend:1.0.0

3. Configuration and Secrets

A Kubernetes ConfigMap is used for non-sensitive configuration such as database hostname, database port, database name, backend port and the internal backend URL. Below is a screenshot from Rahti showing the ConfigMap (figure 7) and some of the non-sensitive data.

Database credentials are stored separately in a Kubernetes Secret. This prevents passwords from being stored directly inside the container images or normal configuration files. Below is a screenshot from Rahti showing the Secret used for this assignment (figure 8) and the protected variables.

4. Networking

Kubernetes Services are used for communication between the containers. The frontend accesses the backend using the internal address backend-service:3000, while the backend accesses MySQL using mysql-service:3306.

A public Rahti Route was created only for the frontend, as seen in figure 1. TLS edge termination was enabled on the Route (figure 9), and HTTP requests are redirected to HTTPS.

Database Persistence

The MySQL database uses a Kubernetes PersistentVolumeClaim so that the database files are stored separately from the MySQL pod itself.

To test the persistence, I first increased the database-backed counter to a known value (figure 1).

Next, I took a screenshot of the currently running pods for reference (figure 2).

I then manually deleted the MySQL pod and immediately saw the old pod terminating and a new one being created (figure 3).

The new MySQL pod was created using the same persistent volume as the old one. Because of this, once the pod was running, the app still displayed the same counter value of 6, which confirmed that the data was truly being stored inside the persistent volume and not inside the pod itself.

Result

The database data remained available after replacing the MySQL pod. This shows that the PersistentVolumeClaim successfully separates the lifetime of the database data from the lifetime of individual pods.

Pod Recovery

The backend Deployment was configured to run one replica. To test Kubernetes recovery, I manually deleted the running backend pod. Similar to the database persistence experiment, as soon as I deleted the original backend pod a new one started spinning up (figure 1).

The application continued functioning normally after the replacement pod had started.

What Recreated the pod?

The backend is managed by a Kubernetes Deployment. The Deployment manages a ReplicaSet (figure 2), which is responsible for maintaining the requested number of pod replicas.

When the backend pod was deleted, the ReplicaSet detected that the desired replica count of one was no longer satisfied and created a new pod automatically.

Backend Scaling

The backend Deployment was initially configured with one replica (figure 1). To test Kubernetes scaling, the replica count was increased from one to three (figure 2).

Kubernetes created two additional backend pods so that three replicas were running at the same time (figure 3).

Service Communication

The frontend did not need to know the address of any individual backend pod. It continued sending requests to backend-service:3000.

The backend Service selects pods using their labels and routes requests to the available backend replicas. After the scaling test, the backend was returned to one replica.

Application Update

The initial frontend deployment used image version 1.0.0. A visible version number was then added to the page, and a new frontend Docker image was built and pushed as version 1.0.1 (figure 1).

The frontend Deployment was updated to use the new image version. Kubernetes then performed a rolling update.

Rolling Update

During the update, Kubernetes created a new frontend pod using image version 1.0.1 while the previous pod was still available. Once the new pod was ready, the old pod was terminated.

The application remained available during the deployment, and after the rollout the webpage displayed version 1.0.1. The below screenshot (figure 2) shows the newly created frontend pod, as seen by its Created timestamp.
